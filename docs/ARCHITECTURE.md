# Архитектура MagicProxy

## Компоненты

### 1. Расширение (Manifest V3) — `extension/`

- **Service worker** (`src/background/service-worker.js`) — центральный оркестратор.
  Держит подключение к нативному хосту, применяет `chrome.proxy`, реагирует на
  команды из UI.
- **Native Messaging клиент** (`src/lib/native.js`) — обёртка над
  `chrome.runtime.connectNative` с request/response по `id` и подпиской на события.
- **Управление прокси** (`src/lib/proxy.js`) — установка/снятие `chrome.proxy`
  для текущего профиля. Именно здесь реализуется «только этот профиль ходит через
  прокси». Два режима: `fixed_servers` (весь трафик, с bypass-списком) и
  `pac_script` с `mandatory: true` (правила по доменам, fail-closed). После `set()`
  проверяется `levelOfControl`: чужое расширение старше нас — ошибка и откат, а не
  зелёная точка над прямым трафиком. Вместе с прокси ставится и снимается политика
  WebRTC `disable_non_proxied_udp` (разрешение `privacy`).
- **Профили** (`src/lib/profiles.js`) — CRUD профилей в `chrome.storage.local`,
  импорт с дедупликацией по отпечатку (тип, адрес, учётные данные).
- **Парсер ссылок** (`src/lib/parse.js`) — `vless://`, `vmess://`, `trojan://`,
  `ss://` (SIP002 и SIP022), `hysteria2://`/`hy2://`, `hysteria://`, `tuic://`,
  `anytls://`, `ssh://`, `socks5://`/`socks4://`, `http(s)://` и base64-подписки →
  нормализованный профиль.
- **Локализация** (`src/lib/i18n.js`, `_locales/{en,ru}`) — язык из браузера,
  английский по умолчанию; авторский русский текст разметки остаётся запасным.
- **Popup** (`src/popup/`) — вкл/выкл, выбор активного профиля, статус с портом и
  временем работы ядра, логи ядра (подтягиваются только при раскрытой панели).
- **Options** (`src/options/`) — менеджер профилей (импорт, JSON-редактор с
  шаблонами, экспорт), маршрутизация, обновление ядра, раскрытие обращения с
  данными.
- **Onboarding** (`src/onboarding/`) — страница первого запуска с тремя состояниями
  (готово / хост не установлен / ядро заблокировано).

### 2. Нативный хост (Go) — `native-host/`

- **`cmd/host`** — точка входа. Читает/пишет кадры Native Messaging из stdin/stdout.
- **`internal/messaging`** — фрейминг Native Messaging (4-байтный little-endian
  префикс длины + UTF-8 JSON), диспетчер запросов.
- **`internal/core`** — менеджер процесса sing-box: запуск/остановка, слежение
  за выходом (намеренная остановка событий не порождает), проксирование логов в
  расширение без ANSI-кодов, стабильный порт, рабочий каталог на процесс в
  `%TEMP%\magicproxy\host-<pid>` с удалением конфига при остановке и каталога при
  выходе. На Windows хост помещает себя в Job Object с `KILL_ON_JOB_CLOSE` —
  ядро не переживает хост ни при каком способе его смерти.
- **`internal/config`** — генератор `config.json` для sing-box из нормализованного
  профиля: `mixed`-inbound (SOCKS5+HTTP на одном порту), нужный outbound, два
  DNS-резолвера (назначения — через туннель, имя самого сервера — напрямую),
  правила «LAN → direct». Обязательный `hostKey` для SSH. Проверяется тестами
  через настоящий `sing-box check`.
- **`internal/updater`** — проверка и установка свежего ядра с GitHub с
  таймаутами, в горутине, с запретом смены мажорной версии.
- **`internal/diag`** — детект чужого TUN-адаптера, объясняющий «reality
  verification failed» по-человечески.

### 3. sing-box (ядро) — `vendor-bin/`

Внешний бинарник. Делает всю реальную работу транспорта. MagicProxy его только
конфигурирует и запускает.

## Поток «включить прокси для профиля»

```
Popup: клик «Вкл» (профиль X)
   │
   ▼
service-worker: native.request("start", {profile:X, inbound:{port:0}, routing})
   │
   ▼
Go host: config.Build(profile) → config.json
         core.Start(singbox, config.json)  → слушает 127.0.0.1:PORT (mixed)
         ответ: { listen:"127.0.0.1", port:PORT }
   │
   ▼
service-worker: proxy.apply({mode, socks:`127.0.0.1:PORT`})  // только этот профиль
   │
   ▼
Готово. Трафик профиля → sing-box → VLESS-сервер.
```

Выключение — обратный порядок: `proxy.clear()` затем `native.request("stop")`.

## Пер-профильность

`chrome.proxy.settings.set({ scope: "regular" })` действует на профиль, в котором
запущено расширение. Разные профили Brave — разные инстансы расширения с
собственным `chrome.storage` и собственным `chrome.proxy`. Поэтому «профиль A
через сервер 1, профиль B напрямую» получается естественно: в каждом профиле своя
конфигурация MagicProxy.

Каждый профиль браузера запускает **свой** экземпляр хоста (браузер поднимает его
по Native Messaging для каждого подключения) и своё ядро на своём порту. Хосты друг
о друге не знают и не мешают: рабочие каталоги изолированы по PID процесса.

## Маршрутизация: два уровня

1. **В браузере (`chrome.proxy` PAC)** — какие URL вообще идут в локальный прокси,
   а какие — напрямую (bypass). Быстро, на стороне браузера.
2. **В sing-box (`route.rules`)** — из того, что дошло до ядра, что слать в
   VLESS-outbound, а что в `direct`. Нужно для geosite/geoip-правил.

Уровень 1 — основной UI маршрутизации; список «всегда напрямую» действует в обоих
режимах (в режиме «весь трафик» он становится `bypassList`). Уровень 2 — служебные
правила: приватные адреса и локальные имена (`.local`, `.lan`, …) идут напрямую.

## Надёжность

Намерение пользователя (`desired`) лежит в `chrome.storage.local` и переживает
смерть service worker'а; `reconcile()` приводит реальность к намерению по
будильнику раз в 30 с, при пробуждении воркера, при открытии попапа, при событии
`proxy.settings.onChange` и немедленно при неожиданной смерти ядра. Отказ хоста —
fail-closed: `chrome.proxy` остаётся указывать на мёртвый порт, пока не восстановится.

## Что сознательно не сделано

- Один процесс ядра на несколько профилей — не нужно: изоляция по профилю проще
  и безопаснее, а ресурс sing-box невелик.
- Загрузка подписок по URL — пока только вставка содержимого.
- TUN-режим — противоречит идее «только этот профиль».
- macOS/Linux — хост переносим (Go), нет только регистрации Native Messaging
  (plist/JSON-манифесты) и установщиков.
