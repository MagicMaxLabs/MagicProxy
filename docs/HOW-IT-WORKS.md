# Как MagicProxy работает от и до

Полная ментальная модель: от нажатия кнопки до пакета, ушедшего через сервер.

## 0. Одна фраза

Расширение в конкретном профиле браузера говорит `chrome.proxy`: «весь трафик
этого профиля — в локальный SOCKS5 на `127.0.0.1:PORT`». На этом порту сидит
локальное ядро sing-box, поднятое маленьким нативным хелпером; оно принимает
трафик и уводит его наружу по VLESS/…/твоему протоколу на твой сервер.

## 1. Почему три части, а не одна

Расширение Chromium физически не может само туннелировать VLESS:
- `chrome.proxy` умеет направлять трафик только в **HTTP/HTTPS/SOCKS**-эндпоинт;
- песочница MV3 не умеет открывать сырые TCP-сокеты и слушать порт.

Значит, кто-то **вне** песочницы должен: (а) слушать локальный порт как SOCKS5,
(б) уметь VLESS/Reality/… Это и делает нативный хелпер + ядро sing-box. Отсюда три
части:

```
┌───────────────────────────┐  Native Messaging   ┌────────────────────────────┐
│  Расширение (Manifest V3)  │  (stdin/stdout,     │  Нативный хост (Go)         │
│  • UI (попап/настройки)    │   4-байт длина+JSON) │  • менеджер процесса        │
│  • chrome.proxy профиля    │ ──────────────────▶ │  • генератор config.json    │
│  • правила/маршрутизация   │ ◀────────────────── │  • авто-апдейт ядра          │
└───────────────────────────┘                     └──────────────┬─────────────┘
        браузер запускает хост сам                                │ exec
                                                         ┌────────▼─────────┐
                                                         │  sing-box (ядро) │
                                                         │  VLESS/WG/…      │
                                                         │  mixed inbound   │
                                                         │  127.0.0.1:PORT  │
                                                         └──────────────────┘
```

## 2. Кто есть кто

**Расширение** (`extension/`, JavaScript):
- `popup/` — кнопка вкл/выкл, выбор профиля, статус, логи.
- `options/` — менеджер профилей (импорт ссылок, JSON-редактор с шаблонами),
  маршрутизация, обновление ядра.
- `background/service-worker.js` — «мозг»: хранит намерение, дёргает хост,
  ставит `chrome.proxy`, держит всё живым.
- `lib/native.js` — клиент Native Messaging (запрос/ответ по `id` + события).
- `lib/proxy.js` — установка `chrome.proxy` (fixed SOCKS5 или PAC по правилам).
- `lib/parse.js` — разбор `vless://`/`vmess://`/… и base64-подписок в профиль.
- `lib/profiles.js` — хранение профилей/маршрутизации в `chrome.storage.local`.

**Нативный хост** (`native-host/`, Go, → `magicproxy-host.exe`):
- `cmd/host/main.go` — цикл чтения запросов, диспетчер.
- `internal/messaging` — фрейминг Native Messaging.
- `internal/config` — Profile → `config.json` sing-box (весь «перевод» протоколов).
- `internal/core` — запуск/остановка sing-box, логи, выбор/переиспользование порта.
- `internal/updater` — проверка/скачивание свежего sing-box.

**Ядро** (`vendor-bin/sing-box.exe`) — делает реальную сеть. MagicProxy его только
конфигурирует и запускает.

## 3. Что происходит по шагам, когда жмёшь «Включить»

1. **Попап** шлёт service worker'у `{cmd:"enable", profileId}`.
2. **Service worker** пишет в `chrome.storage.local` намерение:
   `desired = { on:true, profileId, port }` и вызывает `reconcile()`.
3. **reconcile** берёт профиль из хранилища и шлёт хосту запрос `start` через
   Native Messaging: `{ profile, inbound:{port: желаемый}, routing }`.
   - Первое обращение к хосту заставляет **браузер запустить** `magicproxy-host.exe`
     (по записи в реестре, см. §6).
4. **Хост** останавливает прежний sing-box (если был), выбирает порт
   (`ResolvePort`: переиспользует желаемый, если свободен), генерит `config.json`
   из профиля (`config.Build`), запускает `sing-box run -c config.json`.
   Ядро поднимает **mixed-inbound** (SOCKS5+HTTP на одном порту) на `127.0.0.1:PORT`.
   Хост отвечает `{ listen:"127.0.0.1", port:PORT, socks:true, http:true }`.
5. **Service worker** ставит `chrome.proxy.settings` **этого профиля** на
   `SOCKS5 127.0.0.1:PORT` (или PAC-скрипт, если включён режим правил).
6. Готово: любой запрос страницы в этом профиле идёт в локальный SOCKS5 → sing-box
   → по твоему протоколу на твой сервер → в интернет. Значок в тулбаре — зелёный `ON`.

Выключение — в обратном порядке: снять `chrome.proxy`, послать хосту `stop`,
поставить `desired.on=false`.

## 4. Почему именно «один профиль», а не вся система

`chrome.proxy.settings` действует **на тот профиль браузера, в котором запущено
расширение**. Разные профили Brave — это разные копии расширения со своим
`chrome.storage` и своим `chrome.proxy`. Поэтому «профиль A — через Германию,
профиль B — напрямую» получается само собой: в каждом профиле своя настройка (или
её отсутствие). Система и другие приложения не затронуты вообще.

## 5. Как профиль превращается в рабочий туннель (config.Build)

`config.Build(profile)` собирает JSON sing-box:
- **inbound**: всегда `mixed` на `127.0.0.1:PORT` (принимает и SOCKS5, и HTTP).
- **outbound «proxy»**: строится под тип профиля:
  - vless → `{type:vless, uuid, flow, tls{reality/utls}, transport{ws/grpc/…}}`
  - vmess/trojan/shadowsocks/hysteria2/hysteria/tuic/anytls/ssh — каждый в свои поля;
  - **socks/http** → простой апстрим-прокси (http+tls = HTTPS-прокси), с/без auth;
  - **wireguard** → особый случай: не outbound, а верхнеуровневый `endpoints`
    (в sing-box ≥1.11 WG переехал туда), тег всё равно `proxy`;
  - **shadowtls** → цепочка: внутренний протокол (обычно shadowsocks) теряет
    server/port/tls и получает `detour:"shadowtls-detour"`, а рядом появляется
    outbound `shadowtls` с реальным server/port и TLS-камуфляжем.
- **outbound «direct»**: прямой выход.
- **route**: правило «приватные/LAN-адреса → direct» (в современном
  `action:"route"` формате — переживает авто-апдейт ядра) + `final:"proxy"`.

Всё это перед запуском можно проверить командой `test` (хост зовёт
`sing-box check`) — так работает кнопка «Проверить конфиг» в редакторе.

## 6. Установка и связь: Native Messaging + фиксированный ID

- Браузер запускает хост не сам по себе, а по **манифесту Native Messaging**,
  путь к которому лежит в реестре:
  `HKCU\Software\<Browser>\NativeMessagingHosts\com.magicproxy.host`.
  Значение ключа — путь к `com.magicproxy.host.json`, а тот указывает на
  `magicproxy-host.exe` (относительным путём — папка переносима).
- Манифест разрешает подключаться только расширениям из `allowed_origins`. Чтобы
  установщику не спрашивать «плавающий» ID, в манифест расширения зашит **фиксированный
  публичный ключ** (`key`), из-за чего ID всегда один:
  `enhdbompcjbofadainhfppkhahlhbmap`. Поэтому `setup.bat`/инсталлятор ставятся
  **без аргументов**.
- Формат сообщений: 4 байта длины (little-endian) + UTF-8 JSON. Запрос
  `{id,type,payload}`, ответ `{id,ok,result|error}`, плюс события хоста
  `{event:"log"|"state", …}` (логи ядра, падение процесса).

## 7. Что держит прокси включённым (надёжность)

MV3 убивает service worker через ~30 сек простоя, а с ним — native-порт и sing-box.
Чтобы прокси не отваливался:
- **Намерение в storage** (`desired`) — это правда о том, чего хочет пользователь,
  и она переживает смерть worker'а.
- **reconcile()** приводит реальность к намерению. Запускается при пробуждении
  worker'а, по будильнику, при открытии попапа, при старте браузера.
- **Keepalive-будильник** (`chrome.alarms`, 30 сек) пингует хост: (а) держит
  worker живым, (б) если хост/ядро умерли — reconcile поднимает их заново.
- **Стабильный порт**: хост переиспользует прежний порт, поэтому `chrome.proxy`
  почти никогда не надо переставлять — рестарт ядра проходит бесшовно.
- **Fail-closed**: если хост внезапно умер, `chrome.proxy` **не** снимается (иначе
  трафик утёк бы напрямую) — ждём восстановления. Приватность важнее.
- Значок тулбара отражает состояние: `ON` (зелёный) / пусто / `!` (ошибка).

## 8. Приятные штуки вокруг

- **Онбординг-страница**: при установке, если хост не отвечает, открывается
  страница с кнопками «Скачать инсталлятор» / «Проверить снова».
- **Авто-апдейт ядра**: кнопка в настройках — хост тянет последний sing-box с
  GitHub и атомарно заменяет бинарник (с обходом временных локов Defender).
- **Инсталлятор**: Inno Setup (`magicproxy.iss`) — обычный `.exe`, per-user, без
  админа. Собирается в CI по тегу вместе с ядром и портативным zip.
- **Публикация**: `pack-store.ps1` готовит пакет для Chrome Web Store (там ID
  присваивает магазин — его нужно добавить в `allowed_origins`).

## 9. Полный список протоколов

VLESS (+REALITY/XTLS-Vision/ws/grpc/httpupgrade), VMess, Trojan, Shadowsocks
(+ShadowTLS v1/2/3), Hysteria2, Hysteria v1, TUIC, AnyTLS, WireGuard, SSH, а также
апстрим-прокси SOCKS5/SOCKS4/HTTP/HTTPS — с авторизацией и без. Все 16 связок
проверены на sing-box 1.13.14.

## 10. Единственное, что нельзя автоматизировать

Две вещи упираются в платформу и остаются ручными по одному разу: (1) загрузить
unpacked-расширение в dev-режиме (убирается только публикацией в Web Store) и
(2) запустить установщик (реестр/манифест живут вне песочницы). Всё между ними —
без ввода. Полностью «внутри браузера» без хоста нельзя: единственный путь (Direct
Sockets в Isolated Web Apps) недоступен обычным пользователям вне ChromeOS, а Brave
его намеренно отключает.
