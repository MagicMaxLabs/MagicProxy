# Архитектура MagicProxy

## Компоненты

### 1. Расширение (Manifest V3) — `extension/`

- **Service worker** (`src/background/service-worker.js`) — центральный оркестратор.
  Держит подключение к нативному хосту, применяет `chrome.proxy`, реагирует на
  команды из UI.
- **Native Messaging клиент** (`src/lib/native.js`) — обёртка над
  `chrome.runtime.connectNative` с request/response по `id` и подпиской на события.
- **Управление прокси** (`src/lib/proxy.js`) — установка/снятие `chrome.proxy`
  для текущего профиля. Именно здесь реализуется «только этот профиль ходит через
  прокси». Поддерживает три режима: `fixed_servers` (весь трафик), `pac_script`
  (правила по доменам), `system`/`direct` (выкл).
- **Профили** (`src/lib/profiles.js`) — CRUD профилей в `chrome.storage.local`.
- **Парсер ссылок** (`src/lib/parse.js`) — `vless://`, `vmess://`, `trojan://`,
  `ss://`, `hysteria2://`, `tuic://` и base64-подписки → нормализованный профиль.
- **Popup** (`src/popup/`) — быстрый вкл/выкл, выбор активного профиля, статус.
- **Options** (`src/options/`) — полный менеджер профилей, импорт, правила
  маршрутизации, настройки. (добавляется)

### 2. Нативный хост (Go) — `native-host/`

- **`cmd/host`** — точка входа. Читает/пишет кадры Native Messaging из stdin/stdout.
- **`internal/messaging`** — фрейминг Native Messaging (4-байтный little-endian
  префикс длины + UTF-8 JSON), диспетчер запросов.
- **`internal/core`** — менеджер процесса sing-box: запуск/остановка, слежение
  за выходом, проксирование логов в расширение, выбор свободного порта.
- **`internal/config`** — генератор `config.json` для sing-box из нормализованного
  профиля: строит `mixed`-inbound (SOCKS5+HTTP на одном порту) и нужный outbound.

### 3. sing-box (ядро) — `vendor-bin/`

Внешний бинарник. Делает всю реальную работу транспорта. MagicProxy его только
конфигурирует и запускает.

## Поток «включить прокси для профиля»

```
Popup: клик «Вкл» (профиль X)
   │
   ▼
service-worker: native.request("start", {profile:X, inbound:{port:0}, routing})
   │
   ▼
Go host: config.Build(profile) → config.json
         core.Start(singbox, config.json)  → слушает 127.0.0.1:PORT (mixed)
         ответ: { listen:"127.0.0.1", port:PORT }
   │
   ▼
service-worker: proxy.apply({mode, socks:`127.0.0.1:PORT`})  // только этот профиль
   │
   ▼
Готово. Трафик профиля → sing-box → VLESS-сервер.
```

Выключение — обратный порядок: `proxy.clear()` затем `native.request("stop")`.

## Пер-профильность

`chrome.proxy.settings.set({ scope: "regular" })` действует на профиль, в котором
запущено расширение. Разные профили Brave — разные инстансы расширения с
собственным `chrome.storage` и собственным `chrome.proxy`. Поэтому «профиль A
через сервер 1, профиль B напрямую» получается естественно: в каждом профиле своя
конфигурация MagicProxy.

Один нативный хост может обслуживать несколько профилей одновременно — каждый
получает свой inbound-порт и свой процесс sing-box (или один процесс с несколькими
inbound/outbound — см. TODO по мультиплексированию хоста).

## Маршрутизация: два уровня

1. **В браузере (`chrome.proxy` PAC)** — какие URL вообще идут в локальный прокси,
   а какие — напрямую (bypass). Быстро, на стороне браузера.
2. **В sing-box (`route.rules`)** — из того, что дошло до ядра, что слать в
   VLESS-outbound, а что в `direct`. Нужно для geosite/geoip-правил.

MVP использует уровень 1 как основной UI маршрутизации; уровень 2 — для
служебных правил (например, трафик к самому прокси-серверу идёт напрямую).
